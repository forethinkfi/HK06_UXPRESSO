# 06. UX Writing Guidelines

## Tone & Voice

친절하지만 간결하게 · 일상적인 언어 · 행동 중심 · **고객을 탓하지 않음** · 전문 용어 최소화 · 과한 감정 표현 지양 · 화면마다 같은 어미(앱 레퍼런스의 해요체를 계승: `~해요`, `~해 주세요`) [확인: 앱 안내문이 해요체].

## 버튼 문구

| Avoid | Recommended |
|---|---|
| 픽업하기 | 포장하기 (동일 기능인 경우) |
| 확인 | 주문 내역 확인 |
| 다음 | 결제 방법 선택 |
| 옵션 선택 | 추가하고 싶은 옵션이 있나요? |
| 선택 안 함 | 추가 옵션 없이 담기 |
| 담기 | 장바구니에 담기 |
| 초기화 | 전체 주문 취소 |
| 취소 (옵션) | 옵션 선택 취소 |
| 확인 (수정 후) | 변경 내용 저장 |
| 결제하기 | 4,500원 결제하기 |
| 주문 완료 | 주문이 접수되었어요 |

## 안내 문구 (Instruction)

| 상황 | 문구 |
|---|---|
| 주문 방식 | `어디에서 드시나요?` — `매장에서 먹기` / `포장하기` |
| 온도 | `HOT 따뜻하게` / `ICE 차갑게` |
| 샷 | `샷 추가` — 보조 설명 `커피를 더 진하게` |
| 선택 옵션 그룹 | `추가하고 싶은 옵션이 있나요? 원하는 옵션이 없다면 선택하지 않아도 돼요.` |
| 쿠폰 사전 확인 | `쿠폰이 있다면 미리 확인할 수 있어요. 건너뛰어도 주문할 수 있어요.` |
| 카드 | `카드를 단말기에 꽂아 주세요.` |
| 처리 중 | `결제하고 있어요. 화면을 그대로 두고 기다려 주세요.` |

## 오류 메시지 구조

현재 상황 → 확인된 원인 → 주문 유지 여부 → 다음 행동. 원인이 확인되지 않았으면 원인을 지어내지 않고 상태만 안내합니다.

| 상황 | 문구 |
|---|---|
| 쿠폰 적용 불가 | `이 메뉴에는 사용할 수 없는 쿠폰이에요.` + 이유 + `다른 쿠폰 입력 / 쿠폰 없이 결제하기` |
| 최소 주문 금액 미달 | `5,000원 이상 주문할 때 쓸 수 있어요. 2,500원 더 담으면 쓸 수 있어요.` |
| 결제 실패(확정) | `결제가 승인되지 않았어요. {확인된 원인}` + `담은 메뉴는 그대로예요.` + `다시 시도 / 다른 방법` |
| 승인 불확실 | `결제 여부를 확인하고 있어요. 중복 결제를 방지하기 위해 다시 결제하지 말아 주세요.` |
| 필수 옵션 미선택 | `온도를 아직 고르지 않았어요. 따뜻하게 또는 차갑게를 눌러 주세요.` |
| 연결 불안정 | `연결이 불안정해요. 기본 메뉴로 이어갈 수 있어요.` |

## 완료 메시지

`주문이 접수되었어요.` · 주문번호 강조 · `주문번호가 호출되면 음료를 받아 주세요.` (매장 운영 방식에 따라 조정) · `잠시 뒤 처음 화면으로 돌아가요.` (숫자 카운트다운 없음)

## 쓰기 규칙

- HOT / ICE 등 익숙한 관용 표현은 유지, 의미가 분명한 기존 용어를 불필요하게 바꾸지 않음
- 버튼은 누르면 무슨 일이 생기는지 예측 가능하게
- 오류에는 해결 방법을 함께, 고객을 재촉하거나 탓하는 표현 금지(`잘못 입력하셨습니다` ✕ → `번호를 다시 확인해 주세요` ○)
- 핵심 정보를 긴 문장에 묻지 않음 (한 문장 한 정보)
- 확인되지 않은 쿠폰·결제 정책은 단정하지 않음 (`사용할 수 있어요` ✕ → `사용할 수 있는 종류예요. 적용 여부는 주문 내용에 따라 달라요.`)

## 다국어 고려사항

- 언어를 바꿔도 주문 정보 유지, 오류·결제 화면까지 같은 번역 적용
- 텍스트 길이 변화(영어 +30~50%, 일본어·중국어는 줄 높이) 대응: 고정 폭 버튼 금지, Auto Layout + 최대 2줄 허용
- HOT / ICE, 가격 표기(`4,500원`)는 병기·유지
- 번역 문구도 같은 구조(원인 + 해결)를 유지하며, 번역 품질은 원어민 검수 필요
